# 音声文字起こしアプリ 設計ドキュメント

## 1. アプリの目的

会議・説明などの音声ファイル（30分〜3時間程度）を入力し、**AIによる精緻な文字起こし**を行う。
文字起こし結果は後で音声を聞き直しながら確認する用途のため、**ASRの生出力に忠実**であること（LLMによる言い換え・要約・推論的な補完を行わないこと）を最優先する。

## 2. アプリの要件

| 項目 | 要件 |
|---|---|
| 入力 | `.m4a` / `.wav` / `.mp4` 等の音声・映像ファイル、30分〜3時間程度 |
| 処理時間 | 理想15〜30分、最大でも1日以内 |
| 精度 | 精緻な文字起こし。推論・言い換え・要約を混入させない（逐語性重視） |
| 参考資料 | `Reference/` に同名テキストがあれば**成果物チェック用**として利用（文字起こし自体の生成には使わない） |
| 作業範囲 | 本プロジェクトフォルダ（`20261010_Voice_Translate/`）配下のみ。外部コード・他プロジェクトは変更しない |
| ASRエンジン | OpenAI API `whisper-1`（3モデル比較検証の結果、決定。3-2節参照） |

## 3. 設計方針

**「推論させない」原則**：ユーザーが後で音声を聞き直して照合するため、**ASRが出したテキストを後工程のLLMで書き換えない**ことを設計上の絶対ルールとする。

- 使ってよい処理：フォーマット整形（改行・タイムスタンプ付与・話者ラベルの機械的な挿入）
- 使ってはいけない処理：文章の要約・言い換え・文法修正・推測による欠落語の補完・フィラー語（「えっと」「あの」等）の削除判断
- ASR自体の設定でも、`temperature=0`（確定的・最尤出力）を用い、プロンプトで文脈補正を促すような指示は入れない
- Reference文書は**プロンプトにも入力にも使わない**。あくまで「出力後の比較レポート」生成にのみ使用し、人間が確認するための差分情報を出すだけ（本文を書き換えない）

### 3-1. フォルダ構成

```
20261010_Voice_Translate/
├── Code/              # 実装コード
│   ├── DESIGN.md
│   └── ISSUE.md
├── Input/             # 入力音声ファイル（.m4a, .wav, .mp4 等）
│   └── {name}.m4a
├── Reference/         # （任意）チェック用の既存テキスト。Input と同名ファイルがあれば比較対象になる
│   └── {name}.txt
├── Output/            # 文字起こし結果の出力先
│   ├── {name}.txt             # 逐語文字起こし本文（タイムスタンプ付き）
│   ├── {name}_Ver0.1.docx      # Word出力（Sample/の議事メモテンプレート書式。タイムスタンプ無し、【会議内容】以下に本文を貼り付け）
│   ├── {name}.segments.json   # チャンク単位の生データ（タイムスタンプ・信頼度等、やり直し・デバッグ用）
│   └── {name}.check_report.md # Reference と比較した差分チェックレポート（Referenceがある場合のみ）
└── Work/              # 一時ファイル（音声チャンク等）。処理完了後に削除可
```

- `{name}` は入力ファイルの拡張子抜きファイル名。これにより `Input/{name}.m4a` ⇔ `Reference/{name}.txt` ⇔ `Output/{name}.txt` が対応付けられる。

### 3-2. 処理内容

```
[Input/*.m4a, *.wav, *.mp4 等]
     │
     ▼
① 入力検証・メタ情報取得（拡張子、長さ、サンプルレート等。ffmpeg/ffprobeで取得）
     │
     ▼
② 前処理：音声抽出・正規化
     - 動画(.mp4)なら音声トラック抽出
     - モノラル / 16kHz 等ASR推奨フォーマットへ変換（音質劣化はさせない範囲で）
     │
     ▼
③ 無音区間検出によるチャンク分割（VAD）
     - 文の切れ目（無音）付近で分割し、単語の途中で切らない
     - 1チャンク 5〜10分程度を目安（並列化と精度のバランス）
     - チャンク境界に数百msのオーバーラップを持たせ、結合時の欠落を防止
     │
     ▼
④ 並列文字起こし（OpenAI API, temperature=0, 複数チャンクを同時リクエスト）
     - 各チャンクをASRに投げ、逐語テキスト＋チャンク内タイムスタンプを取得
     - 失敗チャンクはリトライ（指数バックオフ、最大N回）
     │
     ▼
⑤ チャンク結合・タイムスタンプ正規化
     - オーバーラップ部分の重複テキストを機械的に除去（文字列マッチングのみ。言い換え判断はしない）
     - 全体を通したタイムスタンプ（mm:ss）を各セグメントに付与
     │
     ▼
⑥ 出力生成
     - Output/{name}.txt … タイムスタンプ付き逐語本文
     - Output/{name}.segments.json … チャンク・タイムスタンプ・信頼度の生データ
     - Output/{name}_Ver0.1.docx … Word出力（下記参照）
     │
     ▼
⑦ （Referenceが存在する場合）チェックレポート生成
     - Reference/{name}.txt と Output/{name}.txt を機械的に diff
     - 一致率、差分箇所一覧（行・タイムスタンプ付き）を check_report.md に出力
     - ※この結果で本文を自動修正しない。人間が確認するための参考情報のみ
```

**処理時間を15〜30分に収める方針**（3時間=180分の音声を想定）：

1. **チャンク分割＋並列リクエスト**：1チャンク約5〜10分単位に分割し、API同時実行数を6〜12程度確保する。
   - 例：180分 ÷ 8分/チャンク ≒ 23チャンク。並列度8であれば概ね3ラウンドで完了。
2. **I/O待ちの並列化**：音声前処理（ffmpeg変換）もチャンクごとにパイプライン化し、ASR待ちと並行して次チャンクの前処理を進める。
3. **API側のレート制限に注意**：OpenAIのRPM/TPM制限に応じて並列度を調整する設定値を持つ（実装時にアカウントの制限を確認）。
4. **タイムアウト・リトライの時間予算管理**：全体処理に対してソフトなタイムアウト（例：45分）を設け、超過時は進捗状況をログに出し、どこまで終わったか分かるようにする（③〜⑤は再実行可能な単位にする）。

並列度・チャンク長・使用モデル名などのパラメータはコード内ハードコードではなく、設定ファイル（例：`Code/config.yaml` または `.env`）に外出しする。

**ASRモデルの選定（決定）**：Input内の既存3ファイル（各8分サンプル）で比較検証した結果、`whisper-1` を採用する（2026-10-12決定）。

比較結果の概要（詳細はTEST.md参照）：
- `gpt-4o-transcribe`：1サンプルで「はい、すいません。」を80回以上繰り返す重大なハルシネーション（無限ループ）が発生。「推論させない・逐語性」の原則に反するため不採用。処理速度も3モデル中最も遅い。
- `gpt-4o-mini-transcribe`：速度は最速だが、1サンプルで同一パラグラフの重複挿入（ハルシネーション）が発生。
- `whisper-1`：3サンプルともハルシネーション・重複が見られず、最も内容が詳細（文字数が多い＝情報の欠落が少ない）。速度は3モデル中最も遅いが、許容範囲。
- さらに、`verbose_json`（セグメント単位タイムスタンプ）に対応しているのは3モデル中 `whisper-1` のみ（実機確認済み）。3章で決定した「話者変更時の改行」機能はこの対応状況に依存するため、この点でも `whisper-1` が唯一の選択肢となる。

**話者分離**：話者ラベル付与（ダイアライゼーション）は行わない。一方、無音区間（ポーズ）が一定時間以上続いた箇所では話者が変わった可能性があるとみなし、機械的に改行を入れる（音声信号の無音長による判定のみで、発言内容からの推論は行わない）。

**フィラー語の扱い**：「えっと」「あの」等のフィラー語はASRの生出力のまま残し、削除・整形判断は行わない（「推論させない」原則に基づく）。

**Word出力（決定）**：ファイル名は `{name}_Ver0.1.docx`（例：`20261006_収支DBの可視化_Ver0.1.docx`）。`Sample/(サンプル)20261007_収支DB_議事メモ_v0.1.docx` の書式（フォント：Meiryo UI、表構成：タイトル行＋日時/場所/参加者/資料、「【会議内容】」見出し、箇条書き）を踏襲した `.docx` を生成する（`src/docx_output.py`、python-docx使用）。
- タイトル：ファイル名（拡張子抜き、例「20261006_収支DBの可視化」）をタイトル行セルに設定
- 日時・場所・参加者・資料：音声から自動取得できる情報が無いため、ラベルのみでセルは空欄のまま出力（手動記入前提）
- 「【会議内容】」以下：Sampleのnumbering.xml（abstractNumId=27/numId=29）の全9階層（ilvl 0〜8、■→➢→✧→●→➢→✧→●→➢→✧の循環）を実測し複製して使用（Word上でTabキーによるレベル変更に対応するため、使用する2階層だけでなく定義自体は9階層すべて複製する）
  - ilvl0「■XXX」：トピック見出し。自動要約はしない（「推論させない」原則に反するため）プレースホルダーのまま出力し、人間が後から書き換える前提
  - ilvl1「➢」：`Output/{name}.txt` からタイムスタンプ行（`[mm:ss - mm:ss]`）を除去した本文を、1行＝1箇条書き項目として貼り付ける（要約・言い換えはしない）
  - 段落前後の余白：python-docx既定テンプレートの余白（段落後10pt・行間1.15倍）はSampleに無いため、Normalスタイルで明示的に0pt・単一行間隔に上書き
- 既知の制限：話者変更改行（上記）がほぼ機能しないため、一部チャンクは➢項目が1つの長い段落になる（ISSUE.md参照、対応は保留中）

## 4. 例外処理（エラー処理）

- チャンク単位の失敗はそのチャンクのみリトライ（全体を再実行しない）
- 一定回数失敗したチャンクは、その区間だけ「[文字起こし失敗：00:12:30-00:20:00]」のようにプレースホルダーを出力し、全体処理は継続する（ユーザーが後で該当区間だけ聞き直せるように）
- 推測で埋めることは絶対にしない（失敗は失敗として明示する）

## 5. その他処理方針

### 5-1. 認証設定

- OpenAI APIキーは環境変数（例：`OPENAI_API_KEY`）から読み込む。コード・リポジトリ内にキーを直接書かない

### 5-2. ガードレール設定

- 本アプリの実装・実行はすべて `20261010_Voice_Translate/` 配下で行う（`.claude/guardrail.json` の `allowedProjectDirs` を本フォルダに設定済み）
- 依存パッケージのインストール等もこのフォルダ内（仮想環境等）で行い、他プロジェクトや環境全体に影響を与えない

## 6. 実装手順

以下の順序で実装を進める（3-2の仕様をコードに落とし込む作業順）。

1. 環境セットアップ（Python仮想環境、ffmpegインストール、依存パッケージ定義）
2. 入力検証・メタ情報取得モジュール
3. 音声前処理（抽出・フォーマット変換）モジュール
4. VADベースのチャンク分割モジュール
5. OpenAI API呼び出し（並列・リトライ・レート制御）モジュール
6. チャンク結合・タイムスタンプ正規化モジュール
7. 出力生成（txt / json）モジュール
8. Reference比較・チェックレポート生成モジュール
9. CLIエントリポイント（`Input/` 内ファイルを指定して一括実行）
10. 実データ（Input内の3ファイル）でのテスト実行・時間計測
11. Word（.docx）出力モジュール（`docx_output.py`）
